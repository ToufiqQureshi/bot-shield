PHASE 2 (Challenge and Continuous Trust) - CURRENT STATUS
Updated: 2026-09-23

Branch: phase2-challenge-trust
Buffy's implementation: 959ab46d (code), a14c344f (docs), both pushed.

Built:
- Guard passes its computed risk score into challenge difficulty selection.
- Signed tokens bind the challenge to a nonce, host, redirect and difficulty.
- Signed failed-attempt cookies escalate difficulty; signed passed cookies
  grant 30/15/5 minute trust according to the solved difficulty.
- Bounded challenge telemetry and browser-class outcome counters.
- Recovery text and retry link when browser verification fails; no-JavaScript
  explanation for visitors who cannot run the puzzle.
- Follow-up hardening: the attempt-cookie issue time is signed and checked by
  the server for a 15-minute expiry. Verify decodes a bounded PNG, checks
  300x150 dimensions and nonblank pixels. Prefix-plus-filler is rejected.
- The local nonce fallback evicts expired/oldest entries in FIFO order instead
  of scanning up to 50,000 entries on every verification.

Verification:
- Full backend go test ./..., go vet ./..., go build ./... pass.
- Canvas blank-image and attempt-cookie-expiry tests went red on deliberate
  regressions and green after restoring the fix.
- PNG verification benchmark: about 0.56 ms and 230 KB allocated per verify
  on this Windows i7-9750H machine. It runs only on suspicious traffic's
  verify path, not on every request.
- Local nonce verification at its 50,000-entry cap: about 0.46 microseconds
  per consume on the same machine.
- Race detector unavailable here: CGO_ENABLED=0 and no working gcc toolchain.

Security limits:
- A scripted client can still create a valid PNG and solve the PoW. The
  challenge increases cost but does not prove a human or a real browser.
- Client-reported automation/headless/elapsed fields remain untrusted.
- Challenge-solved labels are candidates only; the trainer excludes them by
  default and no model trained from them may enforce traffic decisions.
