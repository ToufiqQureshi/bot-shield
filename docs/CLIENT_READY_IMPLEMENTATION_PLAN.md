# HakaiShield client-ready and detection implementation plan

**Date:** 2026-09-24. **Scope:** first managed client, one verified domain and one node; then measured expansion. This is the execution plan. [CURRENT_STATUS.md](CURRENT_STATUS.md) records what already works, [SIGNAL_COVERAGE.md](SIGNAL_COVERAGE.md) inventories live signals, and [CLIENT_PILOT_RELEASE.md](CLIENT_PILOT_RELEASE.md) is the deployment checklist. Code is the final source of truth.

## Decision in one minute

Ship the existing proxy to a **shadow pilot** after the real domain, origin, TLS, auth, and rollback checks pass. Add low-cost, bounded detection in evidence-only mode; label representative traffic; then activate narrowly for the client. Do not promise "80% blocked" until bot recall and human impact are measured on that client's traffic. Feature count cannot establish recall. A defensible 80% claim needs an agreed bot definition, an independent labelled holdout, sample size and uncertainty, plus results by attack class. "Client-ready" means the release gates below pass; it does not mean self-service SaaS is finished.

## Current baseline and constraints

- The Go proxy already observes TLS/JA4, UA/header contradictions, IP and JA4 velocity, path crawling and a honeypot; rule scoring, challenge, signed session cookie, tenant isolation, explainable evidence and shadow policy exist. Client-hint contradictions are shadow-only. Four browser candidates are visible only after an **enforced** challenge solve, so they cannot validate ordinary shadow traffic.
- `backend/pkg/decide` is an immutable, offline-trained logistic model over the nine binary scored checks. It validates version and exact feature order, uses an in-process bitmask dot product, and records opinions in shadow. It has no representative independently verified training/evaluation set, calibration proof, safe rollout switch, or demonstrated advantage over the rules. A challenge solve or honeypot trip is a *candidate* label, not truth.
- The dashboard and managed onboarding are partially ready. The actual client DNS, origin, server, TLS, end-to-end browser paths, latency, evidence retention and commercial/legal details have not been verified. Redis and evidence assumptions are single-node. See [CURRENT_STATUS.md](CURRENT_STATUS.md) for exact verification already completed.
- Two goals must be optimized together: **bot recall at an acceptable human false-positive/challenge rate**, and **monthly cost per protected request/GB**. Inline proxy bandwidth can dominate the bill. A stronger signal that adds network calls or collects unlimited telemetry is not acceptable by default.

## Execution order and release gates

| Stage | Work and concrete output | Gate before proceeding |
|---|---|---|

Use `deploy/README.md` and `CLIENT_PILOT_RELEASE.md`. | Real HTTPS and browser journeys work; login/checkout/API/crawlers survive; restart, Redis outage and rollback are exercised; p95/p99 proxy latency and origin errors recorded. Start in shadow. |
| P1 — measurement | Capture tenant-scoped request volume, action counts, egress bytes, CPU/memory, Redis/DB usage, challenge solves/failures, origin errors and user complaints. Define sampling, retention and a reviewed bot/human labelling workflow. | Client approves a protected-route list, an acceptable human impact budget, the traffic sample and a rollback contact. No performance or recall claim without data. |
| P2 — cheap detection | Implement the P2 rows in the feature table as independent shadow evidence; add tests, feature flags, expiry and per-tenant cost/volume limits. Start with endpoint-aware server signals and safe resource/session summaries. | Offline replay plus real shadow review show an incremental gain against current rules, with browser/device/accessibility slices and no harmful cost/latency regression. |
| P3 — opt-in browser and form coverage | Integrate a first-party, client-approved script on selected pages/forms. Send short-lived, aggregated session summaries only. Document CSP, consent/privacy, fallback and an API-only path. | Normal users on mobile, keyboard, password manager, privacy browser and assistive tech remain usable; bot forgeries are tested; missing JS is neutral. |
| P4 — limited enforcement | Approve a versioned tenant policy for specific routes, canary it, watch error/challenge/complaint rate, and retain instant shadow/allow rollback. Promote `pkg/decide` separately only if its holdout result beats rules. | Observed client traffic meets the agreed recall/human-impact target; owner and client sign off. |
| P5 — scalable product | Durable tenant evidence, self-service DNS proof/ACME, customer-editable policy, metering/billing, multi-node replay/failover, retention controls and support processes. | Required for general self-service SaaS, **not** a prerequisite to an explicitly managed one-domain pilot. |

**Release record:** save domain/origin and deployment version, secret/cert ownership (never secret values), config revision, smoke/load results, cost baseline, labelled evaluation report, chosen policy, rollback command/contact, and client approval. If a gate fails, remain in shadow or postpone routing customer traffic.

Document that installation requirement clearly.

## Behavioural collection contract (P3)

1. Serve a small versioned first-party script from the protected domain on *selected* HTML pages. The managed client approves placement and privacy notice/CSP changes. Keep APIs, webhooks and pages without script functional.
2. Compute a session summary in the browser: event counts, coarse timing buckets, scroll/click/touch ordering, navigation continuity and form modality flags. Never transmit field values, raw keystrokes, raw mouse paths, exact coordinates or stable device fingerprint IDs. Bound payload size, event count, reporting frequency and session TTL; drop excess data.
3. Bind the submission to a short-lived, host/tenant-scoped token; validate body, origin, replay, rate and size at a cheap endpoint. Treat all browser telemetry as attacker-controlled. Missing or invalid summaries are neutral until joined to stronger server-observed evidence.
4. Keep a fixed retention window, explicit deletion, tenant isolation and a visible sampling metric. Start at a low sample rate and cap storage writes. Privacy/legal review happens before real visitor capture.
5. Test desktop/mobile, Safari/Firefox/Chromium, keyboard-only, screen reader, password manager, VPN/private browsing, flaky networks, CSP restrictions and client performance. Replay representative bot frameworks and hand-written telemetry for spoof resistance. Compare incremental detection against request-only rules.

## `backend/pkg/decide`: improve without a cloud inference bill

**Keep:** immutable linear model, versioned feature schema, strict load validation, typed decisions, contributions and in-process no-allocation inference. Keep rule scoring as the safe baseline. There is no reason to add an LLM, remote model service or online retraining to the request path.

1. **Label contract and review:** add a curated label record with tenant, event time, stable *pseudonymous* identity/group, source, reviewer, confidence, feature-schema version and bot class. Candidate challenge/honeypot observations enter a review queue, not the training truth set. Deduplicate/cap identities and keep labels independent of the rule/model decision. Do not train on verified good crawlers as hostile bots.
2. **Leakage-safe evaluation:** split by time and identity/session, with a locked later holdout; exclude related sessions across splits. Report per-tenant and per-attack-class sample sizes, bot recall, **hard-block** human false-positive rate, challenge burden/solve rate, rule-vs-model disagreement, precision at the observed base rate, latency and error bars. Current aggregate accuracy and log loss alone are insufficient. Add Brier/calibration buckets; call `Prediction.Confidence` a margin until calibrated.
3. **Feature evolution:** give each signal stable meaning and schema version. Preserve the nine-bit model contract; add new browser/behaviour features first as separately named shadow observations. When promoting a feature, version training records/model together; reject missing or stale feature schemas, and keep neutral handling for unobserved JS/API sessions. Avoid increasing the 32-bit mask blindly: plan a typed/versioned wider representation before feature 33.
4. **Model lifecycle:** record dataset hash, code/schema version, training options, evaluation report, owner approval and model checksum. Load an approved immutable artifact, compare in shadow by tenant, support immediate disable/rollback. Protect model and label endpoints from tenant leakage and label poisoning.
5. **Promotion test:** on a representative holdout, the model must improve the agreed objective over the existing rule scorer **at the same or lower human harm and acceptable cost**. Then canary by route/tenant with two independent signals for hard block, auditable explanations, alerting and rollback. Until these conditions pass, its output remains shadow-only. Thresholds 0.5/0.9 are training defaults, not production-calibrated policy.

**Likely code touchpoints when implementing:** `pkg/decide/{model,train}*.go`, `cmd/hakaishield-train/main.go`, `pkg/labels/`, `pkg/core/guard.go`, `pkg/evidence/`, signal schema and focused tests. Build tests that fail on group leakage, candidate-label promotion, schema mismatch, misleading aggregate metrics and rollback mistakes before code changes.

## Cloud bill and resource guardrails

- **Measure first:** per-tenant incoming/outgoing bytes, requests, challenge rate, peak/p95 CPU and memory, Redis commands/memory, DB rows/writes, sampled telemetry bytes and provider egress. Dashboard these with a monthly budget alert and a per-tenant traffic/egress ceiling. Billing prices change; compare current official [DigitalOcean Droplet pricing](https://www.digitalocean.com/pricing/droplets), [DigitalOcean bandwidth rules](https://docs.digitalocean.com/platform/billing/bandwidth/), [Supabase plans](https://supabase.com/pricing) and [Supabase egress](https://supabase.com/docs/guides/platform/manage-your-usage/egress) before purchasing. Do not use an old hard-coded monthly estimate as a quote.
- **No per-request paid functions:** no LLM, external reputation/API calls, remote model inference, DNSBL query, geolocation API or headless browser in the hot path. Reuse existing Go proxy, Redis and Postgres only for justified features; static dashboard remains off the proxy's request path.
- **Bound everything:** timeouts, request/body/header sizes, concurrent challenge reservations, per-tenant Redis keys and TTLs, collector samples and payloads, background job frequency, database batches and retention. On overload, shed optional telemetry first; maintain explicit documented enforcement/fail behaviour. Give each new signal a feature flag and measured CPU, memory, latency, storage and egress budget.
- **Make intelligence cheap:** version/expiry-controlled, cached updates with one bounded background refresh; no request-path refresh. Avoid permanent raw event trails and large fingerprint blobs. Use aggregate evidence where it answers the customer question.
- **Control bandwidth:** proxying full origin responses is the unavoidable cost driver. Place the single pilot node close to origin/users, measure actual egress and response sizes, check provider allowance/overage, and agree a traffic cap with the client. Block only with reliable evidence; bandwidth savings do not justify harming humans. Add nodes or services only when p95, availability or capacity evidence requires them.

## Verification and success criteria

For each code slice: follow `CLAUDE.md` test-first and security/cost review, run Go checks from `backend`, run dashboard checks when UI changes, use a real browser for user flows, update `SIGNAL_COVERAGE.md` and `CURRENT_STATUS.md`, and record the decision/evidence. For request-path changes, add adversarial tests for spoofing, tenant crossover, replay, missing JS, overload and false-positive browser cases. Record a benchmark before/after when hot-path work changes.

The client-ready decision requires **all P0 gates**, working shadow observability, a budget/rollback owner, and an agreed route-specific activation plan. Report **hard-block recall** (labelled bots blocked / labelled bots), **intervention recall** (bots blocked, rate-limited or challenged / labelled bots), human hard-block false-positive rate and human challenge burden separately. An "80% bots blocked" claim needs hard-block recall of at least 80% on independent representative labels under a pre-agreed confidence bound and acceptable human impact on the client's traffic; challenge volume cannot be counted as blocks. Report separate outcomes for naive scripts, browser automation, credential attacks and good crawlers; if data are too sparse, report uncertainty instead of a percentage. A managed pilot can begin before that claim is proven, with enforcement left off or limited to reviewed high-confidence routes.
